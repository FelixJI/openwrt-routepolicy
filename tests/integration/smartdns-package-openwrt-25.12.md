# SmartDNS APK 切换隔离验收

在可还原的 OpenWrt 25.12 x86/64 来宾执行。使用来宾自带的 `ucode`、隔离 DNS 上游、本地包介质和控制台。检查的完整设备信息由验收环境保存。

环境搭建见 [可复用隔离实验室](openwrt-lab.md)。域名策略目标与静态 IP 策略目标必须不同，避免静态规则掩盖 DNS 动态集合失效。每次发起新连接，并从 LAN、默认出口和策略出口三份抓包核对握手、源地址转换及响应。

1. 将来宾已装 SmartDNS 的 `packages.adb` 原签名索引与 `smartdns-<版本>.apk` 放在同一个私有目录。记录原包数据库身份及 `/etc/apk/world`，包括其他软件包约束。用 `routepolicyctl smartdns-package-check official TARGET.apk OLD_MEDIA` 检查已知 GitHub 资产，fork 用 `fork`。官方固定资产仍应因 APK 属主而拒绝；修复后的固定 fork 候选应在完整应用依赖环境中通过元数据及单包求解检查。交换旧 APK、损坏字节或替换索引签名应在停服务前拒绝。
2. 当前先实测发行版旧包 → 固定 fork 候选 → 发行版旧包的 `routepolicyctl smartdns-package-switch` 与 `routepolicyctl smartdns-package-rollback`；官方资产正向验收待合格固定版本，当前保留拒绝测试。核对 apk 数据库、包文件归属、运行进程映像、原配置和 90/91 加载状态、原生服务启用状态、回环与接入侧 TCP/UDP 53、上游分组和动态集合。已确认接管期间 dnsmasq 应始终停止并禁用。未接管且 SmartDNS 未启用时，验证 dnsmasq 进程仍提供服务。
3. 在日志落盘但守卫尚未就绪、停止旧 SmartDNS、APK 修改中、候选启动失败和提交标记两侧分别注入故障。验证守卫尚未就绪时恢复只清理日志。覆盖 SSH 退出、进程被杀、断电和恢复再次中断。验证同一启动内由 guard 恢复，断电后在 S18 离线恢复包和持久配置，接管 DNS 由现有 S94/S95 路径恢复。模拟数据库结构可读但 SmartDNS 项缺失，核对签名索引和固定来源旧介质分别只安装原 SmartDNS。模拟数据库损坏、未知包身份和外部配置冲突，核对候选自启动被隔离，日志和外部数据保留。复查旧 APK 可实际安装，检查 package identity 和业务 DNS 查询结果。

官方 Release48.4 固定制品仍因 ACL 拒绝。修改版入口现固定为 PR #10 已合并代码的 CI 测试构建，尚非 Release：run `43664354495`、artifact `14141796762`，文件 `smartdns.1.2026.11.15-2.x86_64-openwrt-all.apk`。GitHub 对下载归档给出的权威 digest 为 `7649ea32e177acf7274f8a16971c99b8e8314fbeda9c417919b09e0a95e347bd`；验证该归档后得到其内 APK 的既有来源准入摘要 `3d27484fa8f188dd6ed58d3db6eacb427def08a8f40c170c275c545153aa041c`。准入摘要由包切换入口消费，不匹配就在停服务前拒绝。归档中的构建提交 `cf5b26d7c7e3879b2048fa5494cc0984f069f998` 与最终合并 `b022bc3e895346cc4925071fb400ed6806489497` 的 Git tree 相同。制品预计于 2027-02-13 过期；过期或未来版本不能静默替代这一固定身份。在线制品过期不影响已保存且验证通过的本地 APK 用于离线回退。

隔离 OpenWrt 25.12.1 已用该 CI APK 验证原生安装、版本执行、配置与 dnsmasq 保持，以及离线恢复旧 SmartDNS。必须使用完整应用依赖：`bind-dig → bind-libs → libopenssl3` 保留库，因此往返都只有 SmartDNS 一个动作。仅安装 SmartDNS 的简化探针会清理库，现有单包计划门禁会拒绝这种环境；不为此扩大事务或改变其他包约束。已验证原生缓存恢复受损 SmartDNS 二进制；这些包管理器探针不替代产品事务、断电和最终整机验收。

产品事务的诊断机验证也已完成一次未接管状态的往返：原生 SmartDNS 的 UCI `enabled=0`、进程未运行，但启动链接已启用；往返后保持这三个状态，dnsmasq PID、五份配置与旧 SmartDNS 二进制保持不变。回退将 SmartDNS 的 APK 约束固定为 `smartdns=46.1-r1`，其他包约束不变。诊断机手工投放过修复，因此该结果只证明事务行为，不能替代最终安装包在干净来宾的验收。

2026-11-15 的 r20 候选安装包已在官方 25.12.1 干净来宾验证未接管状态的往返、真实 LuCI 初始化确认、受管状态的 46.1-r1 与固定修改版往返。域名策略目标 `203.0.115.18` 与静态策略目标 `203.0.115.19` 分别通过策略出口，默认域名和默认 IP 对照通过默认出口，四条新 TCP 连接均有完整握手及 HTTP 200 抓包证据。进入 `apk-attempted` 阶段后杀死事务进程，守卫恢复原包、五份配置和 DNS 服务；该时点不证明已经进入 APK 数据库写入。恢复后真实客户端三类流量仍可用。另一次初始化未在窗口内确认，后端按期回滚。本记录不代表 #21 的单臂、固件升级、全部断电故障与最终提交门禁已完成。

同一 r20 制品的修改版配置还通过了整机重启、SmartDNS 重启、fw4 重载及连续两次应用。开机恢复完成后 SmartDNS 自启、dnsmasq 保持禁用，域名与静态 IP 的客户端新连接可用。断开策略出口时策略目标被拒绝、默认目标仍可用，重连后两者恢复；两组受控上游同时停止响应时，已经预热的域名缓存仍可供客户端建立新连接。

r20 在官方 ext4 镜像执行退出时发现 inode 耗尽：块空间仍余约 22 MiB，但复制第四份字段记录失败。失败未覆盖原确认记录，客户端仍能通信。r22 在确认记录与当前记录完全匹配后退休重复字段副本，保留原始恢复记录。通过实际 APK 升级、重启后，事务普通文件从 3800 减至 2568，DNS 恢复就绪；同一镜像退出完成且无恢复冲突，随后受支持卸载入口成功删除双包并核实 rpcd 的 rc/uci 对象保留、RoutePolicy 对象与程序移除。没有扩容镜像或删除唯一恢复记录来绕过该故障。

r22 单臂来宾从官方 25.12.1 镜像安装后，经真实浏览器选择 `lan` 同时作为接入与默认出口、独立 `eth2` 作为新建 DHCP 策略出口。向导最终确认，SmartDNS 自启且 dnsmasq 禁用。三接口抓包证明四条新连接的握手和 HTTP 响应：默认域名与默认 IP 经 `10.21.1.16`，策略域名 `203.0.115.18` 与独立策略 IP `203.0.115.19` 经 `10.21.2.15`。浏览器确认请求曾超过 XHR 等待时间，页面随后按后端状态显示确认成功，未重复提交。

同一单臂实例完成官方 25.12.1 → 25.12.2（`r32802-f505120278`）真实 `sysupgrade`。升级前核对备份保留五份配置、人工规则及 active/source/confirmed，排除 current 与程序文件；目标官方签名依赖先在可丢弃文件系统中离线实装验证。升级后用同一 r22 介质重装，五份配置逐一比较不变，`init-repair` 恢复 active DNS 就绪，真实客户端默认域名、策略域名及静态策略 IP 新连接均成功。current 未被备份，因此 `init-status.phase=absent` 与存在有效 active 记录同时出现是预期状态，不代表丢失配置。
