目标环境为 OpenWrt 25.12.0 x86/64。客户端、两个出口、DNS 上游及 HTTP 目标均为隔离实验数据，网络未桥接宿主或家庭 LAN。此记录区分上游能力测试与应用代码验收。

## 三版本能力对照

在同一受控上游配置下，三个版本均通过以下检查。

- 默认组通过 eth0 查询，策略组通过 eth2 查询。两侧抓包和上游查询计数核对实际出口。
- 冷查询成功，将响应地址写入对应 nftset。
- 开启缓存后保持同一进程，再次查询成功且上游计数不增加，确认缓存命中。
- 清空两个集合的元素后，同名缓存查询成功，但集合仍为空。
- 删除并重新创建两个集合后，同名缓存查询仍不会回填。
- 未缓存的新子域随后触发上游查询并写入集合，排除 nft API 或权限失效。

因此应用重建规则时必须保护动态分类状态，不能依赖下一次缓存查询补回集合。

## 修改版直接监听 53

修改版固定标签为 `nightly-20260905-014917-c27671b-33937234477-1`。二进制和 APK（资产 545212318）均按 GitHub 资产摘要验证；APK 默认验签返回 UNTRUSTED，未安装或修改来宾信任密钥。实验在临时目录使用该版本二进制及从 APK 读取的原生 init 副本，仅将其 procd 可执行路径改为临时二进制路径；未替换系统 init 或包数据库。

原生配置使用 port=53、tcp_server=1、ipv6_server=0、force_aaaa_soa=1、bind_device=1、bind_device_name=br-lan，以及受控的默认组和上游接口。生成的 UDP/TCP 监听均限于 br-lan 和 lo。

- LAN 与回环的 TCP/UDP 查询均返回两组预期 A 地址。
- AAAA 返回 NOERROR、空 ANSWER 和 SOA，上游日志无 AAAA 转发。
- LAN 的 DHCP 客户端发送两次 DISCOVER，未获得租约。
- 明确临时放行 WAN 输入 53 后，受限设备绑定仍使 UDP 超时、TCP 拒绝；仅移除设备绑定后，同一路径查询成功。测试结束已恢复绑定并删除临时放行规则。
- 冷查询写入正确集合；同进程热缓存命中在清空或重建集合后仍不回填，上游计数不变；新子域查询可重新写入。修改版也不能替代应用对动态集合的保护。

上述为能力对照，dnsmasq 使用 port=0 共存。用户后来要求的 dnsmasq stop+disable、SmartDNS enable，以及失败恢复和重启行为，须另由应用最终提交的集成验收覆盖。

## 早期仅回环监听对照

以下为选型时的历史能力实验。当前初始化接线已改为 SmartDNS 直接监听接入设备及回环设备的 IPv4 TCP/UDP 53；此处的 6053 实验不作为该接线的验收证据。

OpenWrt 官方 46.1 init 的 bind_device=1、bind_device_name=lo 会生成重复的 @lo 绑定行，实测启动以及本机 TCP/UDP 6053 查询均成功。netstat 的通配地址显示不能单独判断外部访问能力。

先在来宾防火墙明确允许 6053，并用开放绑定验证 LAN/WAN 的 TCP/UDP 查询成功，再切换 @lo。LAN/WAN 的四条外部查询路径均被拒绝或超时，本机查询仍成功。auto_set_dnsmasq=0 下，dhcp 配置与实验前相同。
